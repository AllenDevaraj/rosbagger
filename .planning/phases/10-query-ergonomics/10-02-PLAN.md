<objective>
Generalize the schema layer's existing heavy-blob `include=` column filter into a second, orthogonal projection filter `restrict=` (QURY-09). Four functions gain a `restrict: set[str] | None = None` parameter: `TableSchema.arrow_schema`, `TableSchema.column_names`, `build_arrow_table`, and `flatten_message`. When `restrict` is a set, only columns whose dotted name is in it survive — and `flatten_message` simply never reads a dropped column's value off the message (the literal "pushdown", D-06). When `restrict is None` (the default), behavior is byte-for-byte today's.

Purpose: this is the materialization mechanism for projection pushdown. It is self-contained in the schema layer (no `query.py` change) and fully unit-testable here. Plan 10-03 wires it: it computes the restrict set from the alias-expanded SQL, unions the four standard columns (D-07), and passes `restrict=None` under a `SELECT *` (D-08).

Output: edits to `schema/model.py` + `schema/flatten.py`, and `restrict=` unit tests appended to `tests/test_schema_arrow.py`.
</objective>

```python
def column_names(self, include: set[str] | None = None) -> list[str]:
    allowed = include or set()
    return [col.name for col in self.columns if not col.is_heavy_blob or col.name in allowed]

def arrow_schema(self, include: set[str] | None = None) -> object:
    import pyarrow as pa
    allowed = include or set()
    fields = [
        pa.field(col.name, col.arrow_type, nullable=True)
        for col in self.columns
        if not col.is_heavy_blob or col.name in allowed
    ]
    return pa.schema(fields)
```

From packages/rosbagger-core/src/rosbagger_core/schema/flatten.py:
```python
def flatten_message(msg, schema, *, include=None) -> dict:
    allowed = include or set()
    return {
        col.name: reduce(getattr, col.ros_path, msg)
        for col in schema.columns
        if _is_data_column(col) and (not col.is_heavy_blob or col.name in allowed)
    }

def build_arrow_table(messages, schema, *, include=None) -> pa.Table:
    arrow_schema = schema.arrow_schema(include=include)
    kept = [col for col in schema.columns if col.name in arrow_schema.names]
    values = {col.name: [] for col in kept}
    for msg in messages:
        body = flatten_message(msg.msg, schema, include=include)
        for col in kept:
            value = body[col.name] if _is_data_column(col) else getattr(msg, col.name)
            values[col.name].append(value)
    arrays = [pa.array(values[field.name], type=field.type) for field in arrow_schema]
    return pa.table(arrays, schema=arrow_schema)
```

VERIFIED filter semantics (10-RESEARCH Patterns 2 & 3): a column is materialized iff
`(NOT heavy_blob OR name ∈ include) AND (restrict is None OR name ∈ restrict)`.
The only production caller of these four is `backend/query.py` (Plan 10-03 wires it); `inspect.collect_table_schemas` does NOT call them — so a default `restrict=None` leaves `bagq tables` untouched.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| restrict set (from parsed SQL, downstream) → schema filter | The `restrict` set is computed by the orchestrator (Plan 10-03) from the user's alias-expanded SQL via `referenced_columns` — names already inside the sqlglot AST. These functions only TEST membership (`name in restrict`); they interpolate nothing and emit no SQL. |
| message body → flatten read | `flatten_message` reads attributes off an already-deserialized message (the reader's boundary). `restrict` only ever REDUCES which attributes are read — it cannot widen the read surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-04 | Information disclosure | restrict dropping a needed standard column | mitigate | These functions do NOT special-case standard columns; D-07's always-materialized guarantee is enforced upstream by the orchestrator unioning `{t,t_ns,stamp,topic}` into the restrict set (Plan 10-03 owns + tests this). A bare `restrict={"linear.x"}` here legitimately yields only `linear.x` — correct unit-level behavior; the standard-column safety net is integration-tested in 10-03 (Pitfall 3). |
| T-10-05 | Tampering | post-build column drop leaking the read | mitigate | The pushdown is the SKIPPED `reduce(getattr,...)` in the comprehension predicate, NOT a post-build `drop_columns` (which would still read the value — Don't Hand-Roll). Acceptance criteria grep-gate that no `drop_columns`/`.select(` was introduced; the spy test proves the value is never read. |
| T-10-06 | Denial of Service | pathological restrict set | accept | `restrict` only ever filters the existing declared column set (membership test, O(columns)); it cannot add work or unbounded recursion. The projection strictly REDUCES materialization vs today. Offline, single-pass, user's own bag. |
| T-10-SC | Tampering | npm/pip/cargo installs | accept | Zero new packages (10-RESEARCH § Package Legitimacy Audit — pyarrow/rosbags already locked). No install task, so no `[ASSUMED]`/`[SUS]` legitimacy checkpoint applies. |

**Residual risk after mitigations:** No HIGH-severity threats. The projection filter is a pure membership test over an already-declared, value-independent schema; it can only narrow what is read and built, never widen it, and introduces no SQL/identifier interpolation. The standard-column safety net (D-07) is the orchestrator's responsibility and is integration-tested in Plan 10-03.
