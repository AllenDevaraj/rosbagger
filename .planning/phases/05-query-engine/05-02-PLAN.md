<objective>
Build the SQL topic-resolution + orchestration layer on top of the 05-01 backend: parse the user's SQL with `sqlglot`, learn which topics to load, load ONLY those (connection-filtered so unreferenced topics are never deserialized), register each as a DuckDB relation, and execute — returning a `pyarrow.Table`.

Three cooperating pieces:
1. **`backend/resolve.py`** (sqlglot): `referenced_tables(sql)` = `find_all(exp.Table)` MINUS `exp.CTE` alias names (so a CTE is never mistaken for a topic); `referenced_columns(tree)` = `{c.name for c in find_all(exp.Column)}` (a quoted dotted `"linear.x"` parses to `.name == "linear.x"`); `has_star(tree)` = any `exp.Star` (a `SELECT *` produces NO `exp.Column` but an `exp.Star` — it MUST mean "include heavy blobs", RESEARCH Pitfall 3 / A1).
2. **`RosbagsReader.read(*, topics=None)`**: forward a connection filter to `AnyReader.messages(connections=[...])` so only the named topics' raw messages are ever deserialized (RESEARCH Pattern 5 / Pitfall 2 — filter-after-read still pays full deserialization, which violates success criterion #2). Add the matching `topics=` param to the `BagReader` ABC so the seam stays honest (A3).
3. **`backend/query.py`**: `query(sql, reader, *, backend=None) -> pyarrow.Table` — resolve referenced tables/columns/star, build + invert the topic->table map via the shared `TableNameResolver` (skip multi-msgtype topics, mirroring `inspect.collect_table_schemas`), raise a clear error on an unknown table name (lists available tables; Phase 7 owns did-you-mean), then for each referenced topic build its schema, compute the heavy-blob `include` set from referenced columns (`SELECT *` => all that topic's blobs), `reader.read(topics={topic})` lazily, `build_arrow_table`, register into the backend (default `DuckDBBackend`), execute. Lazy-import the heavy stack so `import rosbagger_core` stays light.

Purpose: QURY-05 (resolve referenced topics, load only those) + QURY-06 (execute through the swappable backend).
Output: `backend/resolve.py`, `backend/query.py`, the `read(topics=)` change in reader, two test files.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user SQL string -> DuckDB | The USER supplies the SQL — this is the INTENDED interface of a local single-user CLI, NOT a SQL-injection vector. It is forwarded to `backend.execute` as-is. |
| bag-derived NAMES -> SQL identifiers | Topic/field names become table/column identifiers. Any identifier the code interpolates must go through Phase 3 `quote_ident`. The orchestrator forwards the user's SQL and builds none itself, so no new interpolation occurs — but `register_table` uses the sanitized `TableNameResolver` name (allow-list `[0-9A-Za-z_]`, T-03-01). |
| bag DATA -> Arrow -> DuckDB | Untrusted message values cross as typed Arrow arrays, never as SQL text (handled in 05-01). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04 | Tampering | bag-derived table/column names -> SQL identifiers | accept (mitigated upstream) | The orchestrator builds no SQL — it forwards the user's SQL to `execute`.
