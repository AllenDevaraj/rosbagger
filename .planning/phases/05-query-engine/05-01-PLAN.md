<objective>
Build the `QueryBackend` seam and its DuckDB default impl, and fix the carry-forward WR-01 duplicate-column crash that blocks `build_arrow_table` on real/hostile bags.

Two cooperating pieces, both prerequisites for the 05-02 orchestrator:
1. **WR-01 fix** (`schema/flatten.build_table_schema`): a message body field literally named `t`/`t_ns`/`stamp`/`topic` (or a body name that repeats) currently produces a `TableSchema` with duplicate column names. The name-keyed `values` dict in `build_arrow_table` then collapses columns and raises `ArrowTypeError` (RESEARCH Pitfall 1, VERIFIED reproducible). Rename the colliding **body** column (suffix until unique), keeping its `ros_path` intact so values still extract. Do NOT rename the four standard columns — `t`/`t_ns`/`stamp`/`topic` are the documented QURY-04 contract.
2. **`QueryBackend` ABC + `DuckDBBackend`** in `backend/`: the swappable seam (decision 6) — `register_table(name, arrow)`, `execute(sql) -> pyarrow.Table`, `close()`, plus inherited `__enter__`/`__exit__`. `DuckDBBackend` wraps an in-memory `duckdb.connect()` and returns Arrow via `to_arrow_table()` (NOT deprecated `fetch_arrow_table()`).

Purpose: QURY-06 — execute SQL through DuckDB behind a swappable seam. The WR-01 fix is a hard prerequisite: 05-02 calls `build_arrow_table` on arbitrary user bags, where the collision is reachable.
Output: `backend/base.py`, `backend/duckdb_backend.py`, the WR-01 fix in `schema/flatten.py`, and two test files.
</objective>

The reader/base.py seam pattern this ABC mirrors (stdlib-only abstract contract + inherited context-manager lifecycle):
- `class BagReader(abc.ABC)` with `@abc.abstractmethod` `open`/`close`/`read` and `@property @abc.abstractmethod` metadata; concrete impl inherits `__enter__`/`__exit__`:
  - `def __enter__(self) -> BagReader: self.open(); return self`
  - `def __exit__(self, exc_type, exc, tb) -> bool: self.close(); return False`

Phase 3 schema model the WR-01 fix touches (packages/rosbagger-core/src/rosbagger_core/schema/model.py):
- `@dataclass(frozen=True, slots=True) class ColumnDef:` fields `name: str`, `arrow_type: object`, `ros_path: tuple[str, ...]`, `is_heavy_blob: bool`
- `@dataclass(frozen=True, slots=True) class TableSchema:` fields `table_name: str`, `topic: str`, `msgtype: str`, `columns: list[ColumnDef]`

Current build_table_schema (packages/rosbagger-core/src/rosbagger_core/schema/flatten.py) — the WR-01 fix lands here:
- `STANDARD_COLUMNS: list[tuple[str, pa.DataType]]` = the four `("t", ...)`, `("t_ns", ...)`, `("stamp", ...)`, `("topic", ...)` in fixed order; `_STANDARD_COLUMN_NAMES = frozenset(name for name, _ in STANDARD_COLUMNS)`
- `def build_table_schema(msgtype: str, typestore, *, topic: str) -> TableSchema:` prepends the four standard ColumnDefs (ros_path=()), then `columns.extend(ColumnDef(name=name, arrow_type=arrow_type, ros_path=path, is_heavy_blob=heavy) for name, path, arrow_type, heavy in _walk_fields(msgtype, typestore))`
- `_walk_fields(...)` yields `(dotted_name, ros_path, arrow_type, is_heavy_blob)` leaves in declared order
- `build_arrow_table` builds a name-keyed `values: dict[str, list]` off `arrow_schema.names` — this is why duplicate names collapse and crash (Pitfall 1)

How to craft a collision test type (mirrors tests/test_schema_arrow.py + RESEARCH Pitfall 1): use `rosbags.typesys.get_types_from_msg(msgdef_str, "evil_msgs/msg/Collide")` to register a custom type with body fields named `topic`, `stamp`, `t`, then register into a typestore via `typestore.register(types)`. The ROS2 Humble typestore is `from rosbags.typesys import Stores, get_typestore; get_typestore(Stores.ROS2_HUMBLE)`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bag DATA -> Arrow -> DuckDB | Untrusted message bodies (incl. hostile/odd field names) are materialized into Arrow values, then registered into DuckDB as TYPED values (never as SQL text). This is the crossing this plan hardens. |
| bag-derived NAMES -> SQL identifiers | Topic/field names become table/column identifiers. Already quoted by Phase 3 `quote_ident` (T-03-06); 05-02 interpolates them. Out of scope for this plan (no SQL is built here). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Denial of Service | `build_table_schema` on hostile field names (WR-01) | mitigate | Task 1 renames colliding body columns so a body field named `t`/`topic`/`stamp` no longer crashes `build_arrow_table` with `ArrowTypeError`; regression test pins it. Robustness/availability fix — rated low, not high. |
| T-05-02 | Tampering | bag DATA flowing Arrow -> DuckDB | accept (mitigated by design) | Message values cross as typed Arrow arrays via `con.register`, never concatenated into SQL text. DuckDB ingests Arrow zero-copy as data, not code. No identifier interpolation happens in this plan. |
| T-05-03 | Information Disclosure | DuckDB in-memory connection lifecycle | mitigate | `DuckDBBackend` owns one in-memory `duckdb.connect()` and closes it via context-manager `__exit__`/idempotent `close()` (Pitfall 5) — no leaked connection, no cross-query state. |
| T-05-SC | Tampering | npm/pip/cargo installs | accept | No package installs in Phase 5 — `duckdb`/`sqlglot`/`pyarrow` are pre-existing, pre-installed, locked deps (RESEARCH Package Legitimacy Audit: all Approved, no install occurs). No legitimacy checkpoint required. |
