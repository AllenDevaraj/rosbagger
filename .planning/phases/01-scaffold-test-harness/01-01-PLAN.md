<threat_model>
## Trust Boundaries

Phase 1 is dev infrastructure: no auth, no network service, no untrusted input parsing, no data persistence, no cryptography. (Bag files become untrusted input in Phase 2 — flagged forward, out of scope here.) The boundaries this plan crosses:

| Boundary | Description |
|----------|-------------|
| developer machine → PyPI | ~10 new third-party dependencies are resolved and installed (supply chain) |
| repo build config → uv resolver | unpinned/drifting dependency versions could change API or behavior under us (e.g. the verified rosbags Writer API drift) |

## STRIDE Threat Register

Surface area is intentionally narrow; nothing here is rated `high`.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-SC | Tampering / Spoofing | PyPI dependency resolution (dependency confusion / typosquatting across ~10 new deps) | mitigate | Task 1 blocking-human checkpoint re-verifies each package name+version against PyPI before the first install; all packages are PyPI-verified, established projects (01-RESEARCH.md Package Legitimacy Audit). |
| T-01-DRIFT | Tampering | dependency version pins in the three pyproject.toml files | mitigate | Upper-bounded pins on every runtime dep (notably `rosbags>=0.11,<0.12` to freeze the verified Writer API); plan 01-02 commits `uv.lock` and CI runs `uv sync --locked` for reproducible, tamper-evident installs. |
| T-01-ROS | Tampering (architectural invariant) | offline package metadata | mitigate | Neither `rosbagger-core` nor `bagq` declares a ROS dependency; the offline-import guard test (plan 01-02) actively proves no ROS module leaks into the import graph. |
</threat_model>
