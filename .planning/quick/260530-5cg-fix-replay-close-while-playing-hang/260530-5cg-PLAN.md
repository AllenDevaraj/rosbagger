# Quick Task 260530-5cg: Fix desktop Replay close-while-playing hang

## Problem

`ReplayPanel.closeEvent` calls `stop_thread(self._drive_thread)` (which does
`QThread.quit()` + `wait()`) WITHOUT first pausing the Replayer. The drive worker is blocked
inside `Replayer.run()` — a loop that only returns when state != PLAYING. `quit()` signals the
thread's EVENT LOOP, but `run()` is a blocking call that never reads it, so `wait()` blocks until
`run()` returns naturally (the bag finishes). **Closing the window mid-play of a long bag hangs
the app** until playback would have finished. Found while debugging the pause→play race
(260530-2iv); not user-reported but real (the existing live tests use a tiny 3-message bag that
finishes before teardown, so they never hit it).

## Tasks

1. **replay_panel.py — pause before stop in closeEvent.**
   - In `closeEvent`, BEFORE `stop_thread(self._drive_thread)`: set `self._pending_action = None`
     (so the 260530-2iv deferred-resume path can't restart a drive during teardown) and
     `if self._replayer is not None:` call `self._replayer.pause()` under
     `contextlib.suppress(Exception)` — this sets state=PAUSED + wakes the pacing wait, so `run()`
     returns promptly and `wait()` no longer blocks.

2. **tests/test_desktop.py — regression (offline, fake replayer).**
   - `test_replay_close_while_playing_pauses_and_stops`: a fake replayer whose `run()` blocks on an
     Event until `pause()`; start the drive (worker blocks), then `panel.close()` and assert the
     replayer was paused (`fake.paused is True`) and the drive stopped — proving closeEvent no
     longer waits on a still-PLAYING `run()`. Without the fix the fake is never paused (clean fail
     after the worker's safety timeout), with it the pause is immediate.
